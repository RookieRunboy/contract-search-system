# Proposal: 用户登录与权限控制

- Status: Implemented
- Created: 2025-11-06
- Author: Codex (AI 助手)
- Owners: 平台开发组
- Related Docs: openspec/project.md

## 问题陈述
目前任何访问系统的人都可以直接使用上传、删除等敏感功能，存在以下风险：
1. 合同数据缺乏访问控制，容易发生误删或未授权泄露。
2. 无法区分操作主体，无法审计上传/删除来源。
3. 缺少新用户申请/审批流程，导致账号管理混乱。

## 目标
- 引入登录机制，所有用户需凭账号密码登录后才能访问任何页面。
- 支持两类角色：普通用户（仅访问搜索页）与管理员（可访问上传/管理页）。
- Root 账号为系统内置管理员，可执行全部管理员操作。
- 新用户可提交注册申请（带账号、密码、确认密码），管理员审核后方可生效。
- 管理员可在审批面板中查看待审申请，并选择通过/拒绝。

## 非目标
- 暂不支持 OAuth/SAML 等第三方登录。
- 暂不引入更细粒度的 RBAC（仅两级角色）。
- 暂不实现多因素认证或密码找回流程。

## 方案概览
采用基于会话 Token（JWT 或 HTTP-only Cookie）的登录态，后端维护 `users`、`pending_registrations` 两张存储（可先用数据库或轻量 JSON 文件，后续可抽象为持久化层）。前端新增登录页、注册页、审批管理界面，并在现有页面增加权限守卫。核心流程：
1. 未登录用户被重定向至登录页。
2. 登录成功后根据角色发放 Token，并缓存基础用户信息。
3. 前端路由按角色显示/隐藏菜单，后端在关键 API 进行角色校验。
4. 注册流程写入待审表；管理员在审批页查看详情并审批；通过后创建正式用户。

## 后端改动
1. **数据模型与存储**
   - `User`：`id`（唯一用户名）、`password_hash`、`role`（`normal`/`admin`）、`created_at`、`status`。
   - `RegistrationRequest`：`request_id`、`user_id`、`password_hash`、`submitted_at`、`status`、`reviewer`、`reviewed_at`。
   - root 账号在初始化时写入 `users`，默认 role=`admin`。
2. **API**
   - `POST /auth/login`：接收 `user_id`、`password`，验证后返回 Token + `role`。
   - `POST /auth/logout`：使 Token 失效（若使用黑名单或短期 Token，可省略）。
   - `POST /auth/register`：写入 `pending_registrations`，需校验两次密码一致、ID 未占用。
   - `GET /admin/registrations`：管理员查看待审列表。
   - `POST /admin/registrations/{request_id}/approve`：创建正式用户，删除待审记录。
   - `POST /admin/registrations/{request_id}/reject`：标记为拒绝并记录原因。
3. **权限校验**
   - 现有 `POST /document/add`、`DELETE /document/delete`、`GET /document/list` 等敏感接口需校验 `role=admin`。
   - `POST /document/search` 保持 `normal` 和 `admin` 均可访问。
4. **安全**
   - 使用 bcrypt/scrypt 等算法保存密码哈希。
   - Token 建议设置 30 分钟有效期并支持刷新。
   - 记录登录/审批日志，便于审计。

## 前端改动
1. **路由与守卫**
   - 新增登录页 `/login`、注册页 `/register`。
   - 在 `App.tsx` 中根据登录态渲染受保护路由；未登录时重定向至 `/login`。
   - 根据用户 `role` 决定是否展示上传/管理相关菜单。
2. **登录/注册 UI**
   - 登录页包含账号、密码输入；登录失败给出错误提示。
   - 注册页包含账号、密码、确认密码、提交按钮；提交后提示“等待管理员审批”。
3. **审批面板**
   - 管理员入口（可放在上传页侧边栏或单独页面），显示待审批列表，支持查看详情、同意/拒绝。
4. **全局状态**
   - 在 `frontend/src/services/auth.ts` 增加登录、注销、注册 API 客户端。
   - 在 store/context 中缓存当前用户与角色，刷新页面时尝试自动恢复。
5. **页面权限**
   - 搜索页：所有登录用户可见。
   - 上传页及文档管理组件：仅管理员可访问，普通用户访问时显示无权限提示或重定向。

## 数据流与用户旅程
1. root 管理员登录 → 查看“待审批申请” → 同意新用户申请。
2. 新用户注册 → 申请进入队列 → 管理员同意后收到通知（可先在 UI 上显示状态）。
3. 普通用户登录后只看到搜索页；管理员登录后多看到上传/管理入口。

## 迁移与上线
1. 初始化 root 账号：在部署脚本或迁移脚本中写入默认 root（要求首次登录强制改密码）。
2. 为现有接口增加认证中间件；上线前通过 Feature Flag 控制，逐步强制登录。
3. 发布前更新文档和运维手册，说明如何创建新管理员、重置密码。

## 风险与缓解
- **用户锁死**：若 root 密码遗忘需提供运维脚本重置。
- **审批积压**：考虑添加通知（邮件/站内）减少漏审，可作为后续优化。
- **Token 被窃取**：启用 HTTP-only Cookie + CSRF 防护，或要求前端妥善保管 JWT。

## 测试计划
- 单元测试：密码校验、角色校验、注册审批流程。
- 集成测试：模拟普通/管理员流程，验证受限接口不能越权。
- 前端测试：登录表单验证、路由守卫、审批操作交互。
- 手动验收：新用户注册→管理员审批→登录→执行文档上传/搜索。
